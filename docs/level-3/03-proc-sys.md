# 03 · /proc and /sys: The Kernel's Windows

Linux exposes live kernel state as ordinary-looking files. `/proc` describes processes and system statistics; `/sys` describes devices and drivers and lets you tune them; `sysctl` is a convenience layer over `/proc/sys`. Almost every monitoring tool on Linux (`ps`, `top`, `free`, `vmstat`, `lsof`, `ss`)
is just a reader of these files. Learn to read them directly and you can monitor, debug and write tools without installing anything.

!!! note "What was run"
    macOS has no `/proc` (`ls /proc` fails there; Level 1 · Lesson 02), so **no real /proc file was read** for this lesson. File formats come from `proc(5)`, `proc_meminfo(5)`, `proc_loadavg(5)` (man7.org, October 2026). The parser below was **run on macOS against fixture text I wrote** following those documented formats, so it demonstrates the parsing, not any real
    machine's values. Treat the sample numbers as invented. See Level 1 · Lesson 01.

## What lives where

| Path | Contents |
|---|---|
| `/proc/<pid>/` | One directory per process: `status`, `stat`, `cmdline`, `environ`, `fd/`, `maps`, `limits`, `cwd`, `exe` |
| `/proc/self/` | Alias for the reading process itself |
| `/proc/meminfo`, `/proc/loadavg`, `/proc/uptime`, `/proc/cpuinfo`, `/proc/stat`, `/proc/vmstat`, `/proc/diskstats`, `/proc/net/*`, `/proc/mounts` | System-wide statistics |
| `/proc/sys/` | Tunable kernel parameters (`sysctl`) |
| `/sys/class`, `/sys/block`, `/sys/devices`, `/sys/fs/cgroup` | Devices, block queues, power state, cgroups (v2) |

Everything is generated by the kernel at read time: `cat /proc/meminfo` runs kernel code that formats the current counters. No data is stored on disk, files report size 0, and reads are generally cheap but not free (don't poll `/proc/<pid>/smaps` at high frequency).

## Per-process files

```bash
cat /proc/$$/status | head      # Name, State, Pid, PPid, Uid, Gid, VmRSS, Threads, voluntary_ctxt_switches ...
tr '\0' ' ' < /proc/$$/cmdline  # full command line (NUL-separated)
tr '\0' '\n' < /proc/$$/environ # its environment (needs permission)
ls -l /proc/$$/fd               # open files, symlinks to what they point at (including deleted files!)
cat /proc/$$/limits             # resource limits (open files, processes...)
readlink /proc/$$/exe ; readlink /proc/$$/cwd
```

(Linux; not run.) Highlights: `ls -l /proc/<pid>/fd` shows `(deleted)` for files unlinked while open (Level 1 · 03), and you can recover a deleted but open file by copying from `/proc/<pid>/fd/N`. `cmdline` and `environ` are NUL-separated, not newline-separated. `/proc/<pid>/status` is the human-readable form
and `/proc/<pid>/stat` is the dense, space-separated form that `ps` parses.

## System files and their formats

`/proc/loadavg`, per `proc_loadavg(5)`: "The first three fields are load average figures giving the number of jobs in the run queue (state R) or waiting for disk I/O (state D) averaged over 1, 5, and 15 minutes", the fourth is `runnable/total` scheduling entities, the fifth is the most recently created PID.

```text
0.74 0.58 0.52 2/432 98712         ← fixture in the documented format
```

`/proc/meminfo` is `Name:   value kB` lines (`MemTotal`, `MemFree`, `MemAvailable`, `Buffers`, `Cached`, `SwapTotal`, `SwapFree`, `Dirty`, ...; values in kB):

```text
MemTotal:       16384000 kB
MemFree:          412000 kB
MemAvailable:   12288000 kB
Cached:         11000000 kB
SwapTotal:       2097152 kB
SwapFree:        2097152 kB
```

`/proc/stat` has cumulative CPU time per state in "jiffies" (USER_HZ ticks, 1/100 s on typical systems): `cpu  user nice system idle iowait irq softirq steal guest guest_nice`. **CPU utilisation is the difference between two samples**, never a single reading: `(Δbusy) / (Δtotal)`. Disks: `/proc/diskstats`; network:
`/proc/net/dev`; mounts: `/proc/mounts` (the truth about what's mounted, more reliable than `/etc/mtab` legacy).

### A small parser (run on fixtures)

```python
import re

def parse_meminfo(text):
    out = {}
    for line in text.splitlines():
        m = re.match(r"(\w[\w()]*):\s+(\d+)(?:\s+kB)?", line)
        if m: out[m.group(1)] = int(m.group(2))
    return out

def parse_loadavg(text):
    a, b, c, runq, last = text.split()
    running, total = runq.split("/")
    return {"load1": float(a), "load5": float(b), "load15": float(c), "running": int(running), "total": int(total), "last_pid": int(last)}

def cpu_percent(stat_before, stat_after):
    def vals(s): return list(map(int, s.splitlines()[0].split()[1:]))
    b, a = vals(stat_before), vals(stat_after)
    idle_b, idle_a = b[3] + b[4], a[3] + a[4]                    # idle + iowait
    total_b, total_a = sum(b[:8]), sum(a[:8])                    # user nice system idle iowait irq softirq steal
    return 100.0 * (1 - (idle_a - idle_b) / (total_a - total_b))
```

Run on the fixtures above (macOS, Python 3.14):

```text
parse_loadavg("0.74 0.58 0.52 2/432 98712") → {'load1': 0.74, 'load5': 0.58, 'load15': 0.52, 'running': 2, 'total': 432, 'last_pid': 98712}
parse_meminfo(fixture)["MemAvailable"] → 12288000 kB     available share of MemTotal: 75.0 %
cpu_percent("cpu 1000 0 500 8000 100 0 0 0", "cpu 1300 0 600 8500 150 0 0 0") → 42.10526315789473
```

Check the CPU number by hand: between the two samples, `user+system` rose by 300 + 100 = 400 jiffies, idle+iowait rose by 500 + 50 = 550, and the total rose by 950, so utilisation is 400 / 950 ≈ 42.1 %. (An earlier draft of this paragraph had guessed 40 % by eye; I
replaced it after actually running the function. The point stands: compute CPU from deltas, and verify arithmetic with code.) These are invented numbers in the documented format; they say nothing about any real machine.

## sysctl and /sys tuning

```bash
sysctl net.ipv4.ip_forward                 # read /proc/sys/net/ipv4/ip_forward
sudo sysctl -w vm.swappiness=10            # change now (lost at reboot)
echo 'vm.swappiness = 10' | sudo tee /etc/sysctl.d/60-swap.conf ; sudo sysctl --system   # persist
cat /sys/block/sda/queue/scheduler         # the I/O scheduler in use (Lesson 05)
cat /sys/class/net/eth0/operstate          # link state
```

`sysctl a.b.c` maps to `/proc/sys/a/b/c`. Persist settings in `/etc/sysctl.d/*.conf`. Writing to `/sys` and `/proc/sys` changes live kernel behaviour with no confirmation: test on a non-production machine, and record every change (configuration drift again; Level 4 · 03).

## Permissions and hidepid

By default any user can read many `/proc/<pid>/` files of other users (process names, command lines, which may include **secrets passed as arguments**). Never put passwords on command lines. The `hidepid=` mount option for `/proc` restricts visibility; systemd's `ProtectProc=` can do it per service.

## How It Actually Works

procfs and sysfs are *virtual filesystems* registered with the VFS (Level 1 · 02). When you `open("/proc/meminfo")`, the VFS routes to procfs code, which on `read` calls a kernel function that formats current counters into the buffer (a "seq_file"). Per-process directories exist only while the process does. Because the data
is produced on demand, two reads see different numbers, and parsing is a race with a changing system: read the file in one `read()` and parse it, don't assume consistency across files. Counters that only increase (jiffies, bytes) need deltas; gauges (`MemAvailable`) are instantaneous.

## Common mistakes

- **Treating a single `/proc/stat` reading as CPU utilisation.**
- **Parsing `ps` output** in tools instead of `/proc` or a library (`psutil`).
- **Putting secrets in command lines or environment**, where `/proc` exposes them.
- **Changing `/proc/sys` or `/sys` settings by hand** and forgetting to persist or document them.
- **Assuming kB means 1000** (it is 1024 in meminfo).
- **Expecting `/proc` in containers to show host values** (it shows the container's cgroup/namespace view for many files).
- **Polling heavy files** such as `smaps` every second across thousands of processes.
